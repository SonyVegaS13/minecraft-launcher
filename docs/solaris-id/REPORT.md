Эта работа продолжает их, использует прежние Identity ID и хеши паролей, не создаёт вторую базу аккаунтов.

## B. API, Identity, сессии и миграции

Основные исходники: [backend/Solaris.Id.Api](../../backend/Solaris.Id.Api/), особенно `IdentityEndpoints.cs`, `AuthSessions.cs`, `ProfileEndpoints.cs`, `ControlEndpoints.cs`, `Model.cs`, `Program.cs`, `SkinPng.cs`.

- Регистрация требует допустимых ника/email, пароля и подтверждения пароля; без подтверждённого email вход закрыт. Сохранены Identity-хеши, lockout, подтверждение email, сброс пароля и authenticator TOTP. Старый универсальный `/register` bypass отключён.
- Случайные opaque access/refresh credentials хранятся в PostgreSQL как SHA-256. Access действует 15 минут, устройство — до 30 дней. Refresh ротируется один раз под блокировкой; повтор уже использованного refresh отзывает устройство. На каждом bearer-запросе проверяются бан, email, сроки, отзыв и security stamp.
- Login, расходование recovery-кода и создание сессии атомарны под блокировкой пользователя. Refresh соблюдает порядок блокировок **пользователь → refresh → сессия**. Устройства можно просматривать и отзывать отдельно; logout не отключает другие устройства.
- Ник меняется транзакционно с сохранением ID и отзывом прежних сессий/игровых доказательств. Текущий и прежние зарегистрированные ники навсегда остаются за тем же ID; владелец может вернуть свой старый ник, другой аккаунт — получить его не может.
- PNG принимается потоком с лимитом 512 КиБ; проверяются структура, CRC, ограниченный zlib-поток и 64×64 RGB/RGBA scanlines. Повреждённые, слишком большие и неподдерживаемые изображения отклоняются. Замена скина использует PostgreSQL upsert.
- Ответы имеют `no-store`/`nosniff`; plaintext запрещён вне явно разрешённого Development loopback. Production игнорирует тестовые исключения и требует постоянный каталог Data Protection. Не включены запись тел/credential headers, query-секретов или EF sensitive-data logging.

Добавлены две **аддитивные** миграции поверх прежних двух:

1. `20261021164937_SolarisIdSessionsAndGameAccess` — устройства, refresh-история, игровые подключения/пропуска/доверенные сеансы, активность и уникальный нормализованный email. Предварительная проверка дубликатов email останавливает обновление без удаления/слияния пользователей.
2. `20261021165655_PermanentNicknameOwnership` — постоянные резервации ников с backfill текущих имён существующих Identity-аккаунтов. Имена, изменённые **до** миграции и отсутствующие в старой схеме, автоматически восстановить нельзя; для них нужны проверенные оператором записи владения.

`EnsureCreated`, очистка пользовательской базы и автоматическое слияние аккаунтов не применяются. Проверка upgrade выполнялась только в созданной тестом изолированной базе; искусственные строки проверяют сохранность колонок/ID, а действительный парольный вход покрывает отдельный HTTP-набор.

## C. Лаунчер и пользовательский профиль

Основные изменения: `SolarisCloudClient.cs`, `SolarisCloudSync.cs`, новые `SolarisIdTransport.cs`, `SolarisIdConfiguration.cs`, `SolarisIdProfile.cs`, а также `MainWindow.xaml(.cs)`, `SolarisControlPanel.cs`, `SolarisSkinPreview.cs`, `SolarisPlaytime.cs`, `SolarisLegacyImport.cs`. Пользовательский сценарий и настройки описаны в [LAUNCHER.md](LAUNCHER.md).

Существующий экран расширен вводом OTP/явно выбранного резервного кода, просмотром профиля и устройств, сменой ника, настройкой MFA и подтверждением игрового кода. Источник API виден до ввода пароля. Несекретный `solaris-id.json` задаёт HTTPS origin и server audience; серверных ключей в нём нет. Официальный origin пуст до реального развёртывания. Сохранённая сессия привязана к точному origin; обычная сборка не принимает произвольный environment override.

HTTP-транспорт сериализует refresh одного устройства, выполняет максимум один повтор запроса и сохраняет точные body/content headers. Отказ refresh инвалидирует сессию; 403 роли/MFA сохраняется как 403. Поздний refresh/HTTP/UI callback после logout или смены аккаунта не возвращает прежние токены/профиль. «Запомнить меня» использует существующий DPAPI CurrentUser. При недоступности API logout удаляет локальную сессию и честно сообщает, что удалённый отзыв не подтверждён.

Профиль получает скин и доверенные часы с API. Наличие старого файла не мешает обновлению скина с другого ПК; отсутствие облачного скина не подменяется сторонним поиском по нику. Локальные часы, очереди и legacy-импорт сохранены отдельно и не прибавляются к доверенному итогу. Старый cloud cache не признаётся доверенным до ответа с `source: trusted-servers`. Записи локальной активности и обновления серверного итога сериализованы.

**Vanilla 26.2 / Java 25 сохранён.** Отдельная кнопка добровольно устанавливает Vanilla 1.20.1 / Java 17 в собственный каталог `solaris-id-clients/vanilla-1.20.1` через имеющиеся механизмы установки/Java/прогресса/отмены. Она не заменяет существующие Vanilla, Modded, модпак, адреса серверов или автообновление. Linux-проверка не скачивала и не запускала клиент Minecraft.

## D. Доказательство игрового подключения и доверенные часы

Исходники: `GameAccess.cs`, `GameModel.cs`, `SolarisIdProfile.cs`; протокол полностью изложен в [CONTRACT.md](CONTRACT.md).

1. Вошедший владелец получает по HTTPS краткоживущий одноразовый пропуск для выбранного audience; в БД остаётся его хеш.
2. Мост создаёт новый случайный connection ID для фактического подключения Minecraft и показывает игроку случайный код. До одобрения действует карантин.
3. Владелец вводит **свой** код в лаунчере и подтверждает аккаунт/сервер/код. API атомарно связывает пропуск с ником владельца, его устройством, audience и конкретным подключением.
4. Мост независимо получает разрешение API и постоянный Solaris user ID. Ник, IP и offline UUID сами по себе не дают доступ; один отображаемый код тоже не является авторизацией.
5. Мост передаёт heartbeat/close с монотонным sequence. Время вычисляет API по собственным часам с ограниченным разрывом heartbeat; повтор события не начисляет время дважды, карантин не начисляет его вообще.

Пропуск живёт 120 секунд, ожидающее подключение — 90 секунд; stale heartbeat отсечён после 45 секунд. API обеспечивает один активный доверенный игровой сеанс аккаунта. Пропуск нельзя перенести на другое устройство/имя/audience, использовать повторно или после logout. Серверные credentials раздельны по audience и не принимаются как пользовательский bearer.

Лаунчер хранит игровой пропуск только в памяти с TTL. Пароли, bearer/refresh, пропуска и серверные ключи не передаются через Minecraft chat, environment/аргументы игрового процесса или логи. При настроенном audience лаунчер остаётся доступен во время игры для ввода кода; без API локальная игра остаётся доступна, защищённый сервер доступа не получает.

## E. Paper и Forge Auth Bridge

Добавлены [bridges/core](../../bridges/core/), [bridges/paper](../../bridges/paper/) и [bridges/forge](../../bridges/forge/). Цели — **Paper 1.20.1 / Java 17** и **Forge 1.20.1 / 47.4.20 / Java 17**, отдельно от существующего клиентского Modded-пакета.

Общий координатор выполняет HTTPS вне игрового потока, передаёт изменения состояния в главный поток сервера, ограничивает очередь/число подключений/ответы/таймауты и закрывает доступ при отказе, просрочке, бане, отзыве или потере подтверждения. Поздний ответ либо callback не освобождает повторное подключение. Disconnect/shutdown удаляют локальное разрешение и выполняют ограниченную по времени очистку API. `solarisId(Player/ServerPlayer)` возвращает постоянный UUID только для живого одобренного подключения.

Адаптеры блокируют защищённые действия до одобрения: перемещение, команды/чат, взаимодействия, инвентарь/creative, урон, подбирание/выбрасывание, снаряды/транспорт и связанные события. Forge дополнительно содержит обязательные серверные Mixin-гейты для пакетов и advancement. Реальная сборка проверила refmap **39/39 packet handlers и 2/2 advancement handlers**. Отсутствие требуемого injection считается ошибкой запуска. Временные привилегии через изменение game mode/invulnerability не выдаются.

**Обе реальные сборки прошли**, с настоящими Paper/Forge API, без подставных Minecraft-классов. Paper JAR: `bridges/paper/build/libs/solaris-id-paper-1.0.0.jar`. Forge выполнил `compileJava`, `jar`, **`reobfJar`** и strict SHA-256 dependency verification; standalone adapter-тестов у Forge нет (`test NO-SOURCE`). Точное окружение и воспроизведение — в [BUILD_STATUS.md](../../bridges/forge/BUILD_STATUS.md).

Forge review artifact текущей среды:

## G. Развёртывание, оставшаяся приёмка и результат

Подготовлены [инструкция и шаблоны развёртывания](../../deploy/solaris-id/README.md): systemd, защищённый env example, отдельные секреты/права, Data Protection, миграции/backup, прямой HTTPS; альтернативный backend Dockerfile с ограниченным build context. Примеры не содержат production credentials и не запускают сервис на внешнем хосте автоматически.

Первый администратор назначается оператором по **явному постоянному UUID** через `--bootstrap-admin`, после подтверждения email и настройки TOTP. Bootstrap не работает по нику и не создаёт второго первого администратора. Последующие grant/revoke выполняются через OTP-защищённый Control с причиной и аудитом. Бан администратора запрещён, последняя admin-role защищена; смена ролей/баны и MFA синхронизированы блокировками. Control не выдаёт пароли, password hashes или session credentials.

Перед пользовательским вводом в эксплуатацию остаётся:

1. Выделить независимый auth-хост/домен с доверенным TLS, PostgreSQL с отдельными migration/runtime правами, постоянными ключами, backup/restore и мониторингом; настроить настоящий SMTP/DNS/отправителя и проверить внешнюю доставку. Продумать retention истёкших refresh/game records с учётом FK.
2. Выполнить native Windows-приёмку UI/DPAPI, сохранения/возврата аккаунта, local import/skin preview, поведения окна/отмены/обоих путей запуска и нового добровольного 1.20.1 клиента. Cross-build/publish этого не заменяет.
3. На отдельных настоящих Paper/Forge-серверах с игровыми клиентами проверить карантин, ручное одобрение, защищённые действия/пакеты, повторные подключения, shutdown, API outage, бан/отзыв и совместимость полного установленного набора плагинов/модов. **Нативный Minecraft client-server E2E не запускался.**
4. Установить каждому тестовому серверу отдельный audience/key, затем после приёмки разместить несекретный HTTPS `solaris-id.json` рядом с EXE. Внешний API пока не настроен; примерный origin не является работающим сервисом. Публикация лаунчера и установка мостов на рабочие серверы — отдельные действия оператора.

Существенные границы сохраняются: Minecraft offline UUID не заменяется постоянным Solaris ID; перенос inventory/advancement и отображение облачных скинов внутри Minecraft требуют отдельной интеграции. Offline-mode может загрузить/передать playerdata до join callback и допускает отдельные transport/duplicate-nickname риски. HTTPS-одобрение не шифрует сам игровой offline-протокол. Гейты событий/пакетов не являются полной песочницей произвольного стороннего серверного мода; эти ограничения описаны в [Forge README](../../bridges/forge/README.md).

Итог этапов A–G: реализация, реальные доступные локальные security-проверки, обе серверные сборки и Windows-пакетирование завершены; конфигурация CI/развёртывания подготовлена. Production-хостинг, внешняя почта, native Windows и Minecraft E2E остаются явно непроверенными. Рабочие серверы, модпак, обновления и пользовательские релизы не развёрнуты этой веткой.

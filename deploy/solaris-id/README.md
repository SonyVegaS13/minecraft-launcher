# Развёртывание Solaris ID (не выполнено автоматически)

Исходники и эти шаблоны не заменяют рабочий лаунчер, Minecraft-серверы или модпак. Ветка feature/solaris-id не запускает пользовательский release workflow. Не копируйте реальные секреты в GitHub, чат, build args, CLI или журналы.

1. Подготовить отдельный auth-хост, .NET8 ASP.NET runtime, PostgreSQL16+, почтовый SMTP submission с STARTTLS и подтверждённым отправителем, домен/доверенный TLS. Solaris ID не должен зависеть от жизненного цикла Minecraft. База/почта/ключи/резервные копии должны иметь отдельные ограниченные права.
2. Собрать backend: `dotnet publish backend/Solaris.Id.Api -c Release -o /OUTSIDE_REPO/solaris-id`. Альтернатива — Dockerfile в каталоге backend с контекстом **только** `backend/Solaris.Id.Api`; секреты/сертификаты не попадают в образ. Docker-вариант слушает HTTPS8443: сертификат и ключи передаются защищёнными mounts/env, а не из примера systemd.
3. Создать отдельного системного пользователя solaris-id без интерактивного входа, `/opt/solaris-id`, `/var/lib/solaris-id/keys` и `/etc/solaris-id`. Каталог ключей принадлежит только сервису (0700), `api.env` — 0600. Заполнить пример **вне checkout**. Runtime PostgreSQL-роль получает только необходимые DML-права/sequence; роль миграций с DDL используется отдельно.
4. Сделать backup и проверить восстановление. Применить EF8 миграции отдельной deployment-ролью через `dotnet-ef database update`, предварительно проверив базу/окружение. Не использовать EnsureCreated или удаление старых аккаунтов. Миграция уникальных email при дубликатах останавливается без удаления; разрешить владение вручную после backup. Миграция постоянных никнеймов резервирует текущие имена всех имеющихся аккаунтов. Новое имя и все прежние имена остаются за тем же ID навсегда. Исторические имена, изменённые вне прежней системы/БД до установки, автоматически восстановить нельзя.
5. Установить systemd unit: предложенный вариант обслуживает HTTPS443 непосредственно через Kestrel, с сертификатом доверенного центра и PEM-ключом в защищённом каталоге. Сервису разрешено только необходимое CAP_NET_BIND_SERVICE; ключ читает только его пользователь/группа. Настроить обновление сертификата и контролируемый перезапуск отдельно. Plain HTTP не открывать. При использовании дополнительного reverse proxy вместо прямого TLS доверять только конкретному известному proxy, не очищать KnownNetworks/KnownProxies; X-Forwarded-Proto должен задаваться самим proxy. Не отключать проверку сертификата. Во всех access/error журналах proxy требуется удаление query/секретов до записи (email-confirmation URL содержит код). Нельзя скрывать ошибки целиком или включать body/header tracing; готового внешнего log-sanitizer здесь нет, поэтому такой proxy требует отдельной проверки оператора. Прямой HTTPS-вариант не создаёт дополнительного proxy-журнала с query.
6. Проверить `/health` по HTTPS, регистрацию/доставку писем/подтверждение/сброс/lockout/отзыв на двух устройствах. Проверить перезапуск с сохранёнными ключами/БД и восстановление backup. Оператор явно создаёт первого администратора по неизменному UUID через `--bootstrap-admin` после подтверждения email и настройки TOTP. Роль не выдаётся по нику. Проверить Control с OTP, обычный пользователь/recovery-only session туда не допускаются.
7. На отдельном тестовом Paper1.20.1 и Forge1.20.1/47.4.20 установить соответствующий bridge JAR. Для каждого сервера выдать отдельный audience/key, закрыть доступ к ключу и задавать его через окружение процесса. Ключ не хранится в лаунчере и не передаётся игроку. Пропуск остаётся в памяти лаунчера/HTTPS API. До одобрения своего кода игрок в карантине; при ошибке API, истечении, бане или отзыве доступ закрыт. Не устанавливать bridge на рабочие серверы до отдельной ручной приёмки.
8. После приёмки разместить несекретный `solaris-id.json` из `docs/solaris-id/solaris-id.example.json` рядом с EXE. Указать реальный HTTPS origin и audience, не IP/секрет. Пустой официальный origin в исходниках не является развёрнутым API. Публикация нового лаунчера игрокам и установка серверных компонентов требуют отдельного разрешения.

## Существенные границы

- Совместимый вход без клиентского мода требует ручного подтверждения кода в лаунчере. Полностью автоматический proprietary handshake здесь не заявляется.
- Solaris ID постоянен при смене ника. Offline Minecraft UUID остаётся метаданными транспорта, а не доказательством личности. Старые ники не передаются другим ID, чтобы не открыть чужие name-derived playerdata. Перенос Minecraft inventory/advancement/skin rendering между никами и серверами требует отдельной интеграции с постоянным Solaris ID; код не имитирует её.
- Серверные часы основаны на собственном времени API и ограниченных heartbeat доверенных серверов. Локальные часы/старые импорты сохранены отдельно и не повышают этот итог. Компрометация серверного ключа требует немедленного отзыва/замены ключа оператором.
- Данные PostgreSQL, SMTP и ключи Data Protection должны резервироваться/защищаться средствами хостинга. Защита каталога не равна шифрованию диска; для хранилища использовать поддерживаемое шифрование и контролируемые backups.
- Перед production нужны проверка реальными клиентами Paper/Forge, Windows DPAPI/UI, настроенный домен/SMTP, нагрузка и backup-restore. Локальные тесты не подтверждают готовность хостинга.
